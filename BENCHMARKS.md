# Benchmarks

Load tests of the LearnIO API on a synthetic 500,000-question dataset, comparing the baseline against four optimizations. Each optimization is a separate tagged commit (`baseline`, `opt-1-indexes`, `opt-2-eager-load`, `opt-3-keyset`, `opt-4-exam-sampling`), and `bench/run_all.sh` rebuilds and re-measures every version from a clean export of its tag.

## Setup

| | |
|---|---|
| Machine | Windows 11 PC, Intel Family 6 Model 183 CPU, 24 logical cores (see `bench/results/environment.txt`) |
| Database | PostgreSQL 16.15, running on the same machine as the API and the load generator |
| API | FastAPI under a single uvicorn process (1 worker) |
| Load | k6 v2.2.0, 20 concurrent virtual users, 30 seconds per scenario, one run per cell |
| Data | 500,000 questions, 40 courses with a skewed size distribution (a few large courses hold most questions), 800 topics, about 1 million question-topic links; generated by `bench/seed.sql` |
| Scenarios | Course `COURSE001` (the largest course); list = page of 20 questions at depth 10,000; exam = 20-question practice exam; "topic filter" adds `topic-3` |

Every run had 0% HTTP errors and 100% of response checks passed (each response had the expected 20 items).

## What each change did

| Change | Effect (end to end) |
|---|---|
| `opt-1-indexes`: composite indexes on `(course_id, id)` and `(topic_id, question_id)` | No clear effect here (within run-to-run noise). The queries were not the bottleneck at this load. |
| `opt-2-eager-load`: load question topics with `selectinload` | **Largest single gain.** The baseline issued one extra query per question to fetch its topics (about 21 queries per request); eager loading uses 2. Listing p50 811 -> 242 ms, throughput 28 -> 92 req/s; exam p50 1075 -> 445 ms. |
| `opt-3-keyset`: keyset pagination and a topic-first query | Fixes the slow tail for topic-filtered listing: p95 2039 -> 387 ms, throughput 26 -> 67 req/s. No effect on unfiltered listing, where the indexed offset scan was already cheap. |
| `opt-4-exam-sampling`: stored random key with an index instead of `ORDER BY random()` | Exam generation p50 434 -> 292 ms and 47 -> 67 req/s (topic filter: 430 -> 306 ms, 44 -> 63 req/s). |

## Caveats

- One 30-second run per cell, on a machine that was also running the database and the load generator. Small differences (for example `opt-1-indexes` vs baseline, or the baseline exam-with-topic p50 being lower than `opt-1`) are within noise; only the large, consistent changes should be trusted.
- The data is synthetic. Real question text and topic distributions will differ.
- The API runs a single worker, so absolute throughput is low; the comparison between versions is what matters.
- The dataset is seeded directly in SQL, so this measures the read path (listing and exam generation), not PDF ingestion.

## Reproduce

```bash
export PGUSER=learnio PGPASSWORD=learnio PGHOST=localhost
bash bench/run_all.sh          # needs k6, psql, and the backend venv active
```

Raw k6 output for every run is in `bench/results/*.json`.
